# DDD: оценка применимости и скоуп

**Дата:** 2026-09-16  
**Стадия воркфлоу:** 1/5 — Assess DDD fit and scope  
**Статус:** proposed (нужно подтверждение владельца домена)  
**Проект:** Marketplace (`dn.marketplace`)

## Scope and assumptions

- Объект оценки: маркетплейс как модульный монолит (account уже в коде; product/order/payment — впереди).
- Эксперт домена: владелец репозитория (гибрид **[D]** / **[I]**, решение №1).
- Не цель этого шага: SQL, entity Product/Order, микросервисы, event store.
- Уже зафиксировано и не пересматривается здесь: Keycloak SSOT, Redis Pub/Sub, outbox write-only, Facade между доменами, rich entity на account.

## Viability check

Полный DDD оправдан, если верны **хотя бы два** пункта.

| Критерий | Вердикт | Факт в проекте |
|---|---|---|
| Сложные или быстро меняющиеся бизнес-правила | **да** | Seller graph + холд (D8), `canTrade`/`canSell`, атомарный резерв без `SELECT FOR UPDATE`, снимок цены, Stripe escrow |
| Несколько команд ломают одну модель | **нет** | Один владелец + агент; коллизии модели — от CRUD-черновика, не от команд |
| Нестабильные контракты интеграций | **нет** | Контракты заданы: Facade, outbox JSONB, HMAC `USER_UPDATED`; меняется реализация, не граница |
| Нужны явные инварианты и аудируемость | **да** | 422 на нарушение правила, `@Version`, outbox в той же TX, сверка G4, идемпотентность вебхуков |

Итог: **2 из 4** — DDD оправдан. Полный DDD (отдельные БД на контекст, event sourcing, CQRS как два хранилища, саги как отдельный процесс) — нет.

## Три уровня, один выбор

| Уровень | Что это | Вердикт |
|---|---|---|
| Simple modular (анемичный CRUD + пакеты) | Уже пробовали на account; выкинули | **отклонён** |
| **Partial DDD** | Пакеты = bounded contexts; rich-агрегаты в core; Facade = published language; outbox = интеграционные события | **рекомендация** |
| Full DDD | Event store, отдельные деплои/БД, саги, полноценный CQRS | **отклонён** — противоречит «без 2PC», «не Kafka», pet-масштабу команды |

Account уже живёт в partial DDD: переходы методами, `AccountView` наружу, ArchUnit режет entity. Product и Order должны копировать этот уровень, не повышать его.

## Что core / supporting / generic (черновик для шага 2)

| Capability | Тип | Почему |
|---|---|---|
| Account (продавец/бан/`canTrade`) | **core** | Без этого заказ запрещён; SSOT ролей не в БД |
| Product (карточка, склад, цена, резерв) | **core** | Дифференциатор: атомарный резерв и цена как инвариант |
| Order (оформление, снимок, статусы) | **core** | Core value: заказ только при `canTrade` + снимок |
| Payment (холд Stripe) | **core** (узкий) | Эскроу — часть сделки, не «просто провайдер» |
| Outbox + уведомления | supporting | Доставка чужих фактов, не смысл маркетплейса |
| Витринный кэш, MinIO | supporting | Нужны, не отличают продукт |
| Keycloak, Postgres, Redis, Stripe API | generic | Покупаем, не моделируем внутри |

## Что сознательно не делаем

- Event sourcing / event store как SoT (источник правды — Postgres + outbox).
- Отдельная read-БД / полноценный CQRS (кэш витрины — не read-model контекста).
- Process manager/saga между доменами: оркестрация заказа — Facade в одной TX, компенсация — явно в спеке Order, не шина.
- Дробить монолит на сервисы ради «чистоты BC».

## Риски, если выбрать не тот уровень

- CRUD на Product (без C0) → снова выброс, как старый account.
- Full DDD до заказа → месяцы на инфраструктуру событий, core value не едет.
- Смешать склад и заказ в одном агрегате → гонки резерва и статусов заказа в одной блокировке.
