# Runbook: настройка и запуск агентского цикла

Порядок не произвольный. Каждый этап заканчивается **условием выхода** — пока оно не
выполнено, к следующему не переходим. Так ломается по одной вещи за раз, а не по пяти.

Справочник по устройству цикла — `docs/agent-loop.md`. Здесь только действия.

**Сквозное правило:** `AGENT_LOOP_ENABLED` остаётся `false` до этапа 7.
Все workflow цикла начинаются с проверки этой переменной, так что до неё ничего
не запустится само, даже если ты случайно повесишь лейбл.

## Этап 1. Смержить ветку в `main`

`workflow_run` и `schedule` берут файл workflow **только с ветки по умолчанию**.
Пока ветка не в `main`, гейт, мерж и сторож не существуют для GitHub.

Открой PR из `claude/epic-planck-mzkub2` в `main` — он заодно станет первой
проверкой нового CI. Цикл на него не среагирует: `AGENT_LOOP_ENABLED` не задана.

```bash
gh pr create --base main --head claude/epic-planck-mzkub2 \
  --title "infra(agents): событийный цикл и CI" --body "Закрывает настройку автопилота."
```

**Здесь ты впервые узнаешь, в каком состоянии тесты.** Автоматической проверки в
репозитории не было никогда: пункт «Прогон тестов» в `TASKS.md` до сих пор помечен
заблокированным, а описание PR #4 заявляет «127 тестов, 0 падений» — но это
утверждение никто не подтверждал, потому что подтверждать было нечем. Красный CI
на этом шаге — не баг цикла, а первое независимое знакомство с проектом.

Что может упасть и что делать:

| Симптом | Действие |
| --- | --- |
| `temurin-25 not found` в `setup-java` | не наблюдалось: CI поднимает `Temurin 25.0.4`. Если всё же — `zulu` или `oracle` в `ci.yml` |
| Падают тесты `*IT` | чинить тесты; это реальные дефекты, а не инфраструктура |
| Rate limit при `docker pull` | добавить логин в Docker Hub или зеркалить образы |
| `fast` зелёный, `full` красный | ровно та причина, ради которой они разделены — смотри отчёт в артефактах |

**Условие выхода:** джобы `fast` и `full` зелёные, PR смержен в `main`.
**Не переходить дальше с красным CI** — он единственный детерминированный гейт,
и весь смысл цикла держится на нём.

### 1.1 Сразу после мержа — прогнать через CI открытый PR #4

PR #4 (`feature/phase-b-account`) — большой доменный PR, написанный третьим агентом,
с непроверенным утверждением о 127 зелёных тестах. Его база — устаревший коммит
`main`, поэтому CI на нём всё равно не запускался бы корректно.

```bash
gh pr update-branch 4          # подтянуть main с новым CI
gh pr checks 4 --watch
```

Это первая реальная работа пайплайна и самая дешёвая проверка его полезности:
либо 127 тестов подтвердятся независимо, либо ты узнаешь, что в `main` едва не
уехало. Любой исход — выигрыш.

**Не мержить PR #4 до этого.** Он написан не тобой и не проверен ничем.

## Этап 2. Починить ArchUnit и закрыть репозиторий

### 2.1 Стор ArchUnit

**Сделано.** Стор закоммичен в `main`, `allowStoreCreation=false`, гейт работает:
пропажа стора ломает сборку, новое нарушение изоляции валит CI.

В сторе восемь нарушений — это ровно задача **B1** из `.agents/TASKS.md`:
`AccountEntity`, `OrderEntity`, `ProductEntity` в публичном `api` вместо `entity`,
`AccountRepository` в `api.repository` вместо `repository`, все `public`.
Правило «DTO не ссылаются на JPA-сущности» нарушений не имеет.

Список должен только уменьшаться. Починил нарушение — перегенерируй стор:
**Actions → ArchUnit Store → Run workflow**. Он прогонит правила и закоммитит
результат сам; локальный JDK 25 не нужен. Без этого шага стор продолжит помнить
уже исправленное нарушение.

### 2.2 Приватность

Settings → General → Danger Zone → Change visibility → **Private**.

Цена: минуты Actions становятся платными (Free — 2000 мин/мес). Если идёшь по пути
VPS, эта цена обнуляется на этапе 4б.

**Условие выхода:** стор закоммичен, `allowStoreCreation=false`, CI зелёный,
репозиторий приватный.

## Этап 3. GitHub App и проверка цепочки

Самый важный технический риск всего проекта: события от `GITHUB_TOKEN` не запускают
workflow. Один маленький опыт снимает его целиком.

### 3.1 Создать App

Settings → Developer settings → GitHub Apps → New GitHub App.

- Homepage URL — любой, webhook **выключить**
- Repository permissions: Metadata `R`, Contents `RW`, Pull requests `RW`,
  Issues `RW`, Actions `R`, Checks `R`
- **Workflows — не выдавать.** Это бесплатный серверный гард: без него GitHub сам
  отклонит любой push, трогающий `.github/workflows/**`. Агенты не смогут
  переписать собственный CI.
- Administration — никогда

Создать, сгенерировать private key (.pem), **Install App** на этот репозиторий.

### 3.2 Узнать логин и id бота

```bash
gh api /users/<app-slug>%5Bbot%5D --jq '.login, .id'
```

### 3.3 Завести секреты и переменные

Секреты (Settings → Secrets and variables → Actions → Secrets):

| Секрет | Значение |
| --- | --- |
| `AGENT_APP_PRIVATE_KEY` | всё содержимое .pem, включая строки BEGIN/END |
| `CLAUDE_CODE_OAUTH_TOKEN` | уже есть; если протух — `claude setup-token` на ноутбуке |

Переменные (вкладка Variables):

| Переменная | Значение |
| --- | --- |
| `AGENT_LOOP_ENABLED` | `false` |
| `AGENT_APP_ID` | id приложения |
| `AGENT_BOT_LOGIN` | `<app-slug>[bot]` |
| `AGENT_ALLOWED_BOTS` | `<app-slug>[bot]` (логин Codex допишем на этапе 4а) |
| `AGENT_MAX_ROUNDS` | `3` |
| `AGENT_MAX_FILES` | `15` |
| `AGENT_MAX_LINES` | `400` |
| `AGENT_STALE_HOURS` | `6` |
| `AGENT_AUTOMERGE_ENABLED` | `false` |

Необязательные переменные с разумными значениями по умолчанию перечислены
в `docs/agent-loop.md` §6.

### 3.4 Лейблы

```bash
for L in plan ready implementing wip review rework approved needs-human paused; do
  gh label create "agent:$L" --color ededed --force
done
```

### 3.5 Проверка цепочки — не пропускать

Заведи тестовую issue, временно поставь `AGENT_LOOP_ENABLED=true` и повесь
`agent:plan`. Достаточно увидеть, что `agent-plan.yml` **стартовал** — что он
успеет сделать, сейчас не важно. Потом верни переменную в `false` и удали issue.

Этим же проверяется вторая половина цепочки: `agent-plan.yml` в конце ставит
`agent:ready` токеном App, а на него реагирует `agent-dispatch.yml`. Если
планирование отработало, а диспетчер не стартовал — разводка токенов сломана
именно там.

Если ничего не стартовало — смотри, кто автор события:

```bash
gh api repos/devDaniilNovikov/Marketplace/issues/<N>/timeline \
  --jq '.[] | select(.event=="labeled") | .actor.login'
```

`github-actions[bot]` означает, что где-то использован `GITHUB_TOKEN` вместо App.

**Условие выхода:** событие, созданное токеном App, запускает workflow.

## Этап 4. Развилка: VPS или Codex Cloud

Дальше два разных пути. **Не делай оба.**

> Если VPS будет в ближайшие дни — иди сразу в 4б и пропусти 4а целиком.
> Фаза 1 существует только чтобы запуститься без своей машины; при наличии VPS
> она чистая лишняя работа: отпадают PAT, `agent-adopt.yml` и все три
> непроверенных звена сразу.

### 4а. Без VPS — Codex Cloud

Подключить репозиторий к Codex Cloud, затем **стоп-гейт из трёх проверок**.

**S1.** Руками написать в тестовой issue:
`@codex создай ветку, добавь файл docs/ping.md со словом ping и открой PR с первой строкой Closes #N`
Проверить: стартовала ли облачная задача и **открылся ли PR без ручного клика**.

**S2.** То же самое, но комментарий отправлен токеном:

```bash
gh api repos/devDaniilNovikov/Marketplace/issues/<N>/comments \
  -f body='@codex повтори то же самое' \
  -H "Authorization: Bearer $AGENT_CODEX_PAT"
```

**Если Codex не среагировал — Фаза 1 невозможна.** Интеграция отклоняет авторов,
не привязанных к аккаунту Codex. Варианты: завести `OPENAI_API_KEY` и перейти на
`openai/codex-action`, либо ждать VPS и идти в 4б.

**S3.** Убедиться, что PR, открытый Codex, запустил `ci.yml`.

Если все три прошли:
- завести fine-grained PAT (только этот репозиторий; Contents `RW`, Issues `RW`,
  Pull requests `RW`, Metadata `R`) → секрет `AGENT_CODEX_PAT`
- дописать логин бота Codex в `AGENT_CODEX_LOGIN` и в `AGENT_ALLOWED_BOTS`

Результаты S1–S3 записать в `.agents/MEMORY.md` — там уже есть таблица решений.

**Условие выхода:** S1, S2 и S3 прошли; PAT и логины заведены.

### 4б. С VPS — свой раннер

```bash
# на ноутбуке, из корня репозитория
scp ops/vps-bootstrap.sh root@ВАШ_VPS:/root/
TOKEN=$(gh api -X POST repos/devDaniilNovikov/Marketplace/actions/runners/registration-token --jq .token)
ssh root@ВАШ_VPS "REPO=devDaniilNovikov/Marketplace RUNNER_COUNT=2 RUNNER_TOKEN=$TOKEN bash /root/vps-bootstrap.sh"

# на сервере — единственный шаг, который нельзя автоматизировать
ssh root@ВАШ_VPS "sudo -u ghrunner -H codex login --device-auth"

# проверка
scp ops/vps-verify.sh root@ВАШ_VPS:/root/ && ssh root@ВАШ_VPS "bash /root/vps-verify.sh"
```

Затем переменная репозитория:

```
AGENT_RUNS_ON = self-hosted
```

Проверить: открыть черновой PR и убедиться, что `fast` и `full` выполнились на твоей
машине (в логе джоба видно имя раннера) и остались зелёными.

Подробности, размер машины и безопасность — `ops/README.md`.

**Условие выхода:** `vps-verify.sh` завершается без ошибок, CI зелёный на своём раннере.

## Этап 5. Включить цикл по частям

Поставить `AGENT_LOOP_ENABLED=true`. `AGENT_AUTOMERGE_ENABLED` при этом
**остаётся `false`** — цикл будет доводить задачи до `agent:approved` и там
останавливаться, а мержить будешь ты, глядя на вердикты.

1. **Планирование.** Завести issue с реальной задачей дорожки **[I]** из `TASKS.md` —
   подходит **G1** (расширить ArchUnit) или поллер outbox из фазы **F**: узкий скоуп,
   есть тесты, домены не трогаются. Повесить `agent:plan`.
   Ожидаемо: Claude дописывает спеку в тело issue и ставит `agent:ready`.
2. **Передача Codex.** `agent-dispatch.yml` постит `@codex` (4а) либо запускает
   `codex exec` (4б). Ожидаемо: появляется PR.
3. **Усыновление и CI.** `agent-adopt.yml` вписывает маркеры и ставит `agent:wip`,
   CI отрабатывает, `agent-gate.yml` переводит в `agent:review`.
4. **Ревью.** `agent-review.yml` оставляет замечания и ставит `agent:approved`
   или `agent:rework`.

**Условие выхода:** задача дошла до `agent:approved` или `agent:needs-human`
без ручного вмешательства в состояния.

## Этап 6. Три задачи с ручным мержем

**Не включать авто-мерж сразу.** Нужна выборка: сколько вердиктов `approve`
оказались ложными. Без этого измерения ты включаешь автомат вслепую.

Прогнать три задачи дорожки **[I]** до `agent:approved` и смержить руками,
каждый раз читая дифф целиком и отмечая: согласен ли ты с вердиктом Claude.

Если хотя бы один из трёх пришлось отклонить — не переходи к этапу 7, а разбери
причину и поправь `.github/agents/review.md`.

**Условие выхода:** три задачи подряд, вердикт ревью совпал с твоим.

## Этап 7. Авто-мерж

1. Защита ветки `main`: required status check **`full`**, squash-only, линейная история.
   **Не включать** «Require approving reviews» — App не может одобрить собственный PR,
   и мерж упрётся в `405`. **Не включать** «Require branches to be up to date» —
   обновление ветки меняет SHA, сбрасывает маркер одобрения и запускает бесконечное
   переревью. Если защита ветки недоступна на твоём плане GitHub — гарды merge-джоба
   остаются единственным гейтом, они для этого и написаны полными.
2. Поставить `AGENT_AUTOMERGE_ENABLED=true`.
3. Начать с `AGENT_MAX_FILES=10`, поднять после первой десятки задач.
4. Включить сторож: он уже на расписании, проверить `gh workflow run "Agent · Janitor"`.

**Условие выхода:** задача прошла путь от `agent:plan` до смерженного PR без тебя.

## Аварийные ручки

| Что случилось | Что делать |
| --- | --- |
| Цикл делает не то | `AGENT_LOOP_ENABLED=false` — останавливает всё, не удаляя workflow |
| Мержит то, что не надо | `AGENT_AUTOMERGE_ENABLED=false` — цикл продолжит работать, но остановится на `agent:approved` |
| Одна задача сошла с ума | повесить `agent:paused` на issue или PR |
| Раннер лёг, задачи висят | `AGENT_RUNS_ON` удалить — вернётся на раннеры GitHub |
| Нужно вмешаться руками | `agent:needs-human` — это состояние никто не потребляет |
| Codex или Claude не отвечают | `@claude` в комментарии работает всегда: `claude.yml` намеренно оставлен на раннерах GitHub |
